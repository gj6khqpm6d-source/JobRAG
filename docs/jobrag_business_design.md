# JobRAG 业务设计骨架

**版本：** v1.1

**状态：** 后续开发指导文档

**适用范围：** JobSpy 抓取的招聘岗位知识库与求职分析系统

**最后更新：** 2026-09-25

## 1. 文档目的

本文档把 JobRAG 从一个“可以检索和问答的 RAG 原型”定义为一个面向求职分析的业务系统。后续功能设计、数据处理、检索策略、评估和运维工作，都应以本文档为业务骨架。

本文档不规定某个具体数据库、Embedding 模型或 LLM 的实现细节。实现可以变化，但不能偏离以下业务目标：

> 针对用户指定的职位类别和筛选条件，从相关岗位中提取、归纳并解释真实招聘要求，并提供可追溯的岗位证据。

每个后续开发阶段遵循以下协作流程：

1. 先提交该阶段的设计和验收标准；
2. 经用户确认后再实现；
3. 完成后进行测试和结果说明；
4. 用户确认当前阶段完成后，再进入下一阶段。

## 2. 业务定位

### 2.1 默认使用场景

JobRAG 的默认模式是 **目标职位类别分析（Role Analysis）**，而不是对整个知识库做无条件统计。

典型问题包括：

- AI Agent Software Engineer 实习岗位通常要求哪些技能？
- 哪些岗位要求 Python、RAG、LangChain 或向量数据库？
- 目标地区的相关岗位中，哪些技能是高频要求，哪些只是加分项？
- 某个岗位的职责和要求是否符合我的背景？

系统应先根据职位、地点、工作类型、经验级别和时间范围筛选相关岗位，再在这个候选岗位集合内进行分析。

### 2.2 两种问答模式

| 模式 | 作用 | 主要输出 |
|---|---|---|
| Role Analysis | 分析多个相似岗位的共性要求 | 技能频率、核心要求、加分项、岗位证据 |
| Job Detail | 分析一个具体岗位 | 职责、硬性要求、加分项、匹配分析、原始链接 |

Role Analysis 是默认模式；Job Detail 用于深入研究某一条具体岗位。

### 2.3 输出原则

每个结论应尽可能包含：

- 分析的职位范围和筛选条件；
- 使用的岗位数量；
- 结论对应的岗位或岗位集合；
- 公司、职位、地点和发布时间；
- 原始岗位链接；
- 数据新鲜度或抓取时间；
- 信息不足时的限制说明。

## 3. 参考的生产级指导原则

这些官方指导文档并不要求所有个人项目使用相同的云服务，但它们对生产级 RAG 的生命周期有一致认识：数据准备、索引和检索只是基础，还需要回答质量评估、数据更新、监控、成本、安全和版本管理。

- [AWS Prescriptive Guidance：Understanding Retrieval Augmented Generation](https://docs.aws.amazon.com/prescriptive-guidance/latest/retrieval-augmented-generation-options/what-is-rag.html) 将生产级 RAG 拆分为连接器、数据处理、Embedding、索引、检索器、基础模型、Guardrails、编排器、用户体验和身份管理。
- [Microsoft Foundry：Retrieval augmented generation and indexes](https://learn.microsoft.com/en-us/azure/foundry/concepts/retrieval-augmented-generation) 将 RAG 流程定义为准备数据、建立索引、构建应用、测试与评估，并强调混合检索、引用、访问控制、Prompt Injection 防护以及延迟和 Token 成本。
- [Microsoft Foundry：RAG evaluators](https://learn.microsoft.com/en-us/azure/foundry/concepts/evaluation-evaluators/rag-evaluators) 区分检索质量评估和最终回答评估，分别关注 NDCG、检索相关性、Groundedness、Relevance 和 Completeness。
- [Microsoft Azure Architecture Center：RAG evaluation phase](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase) 强调评估不是一次性工作，数据、用户问题和系统配置变化后需要持续重新评估。
- [Google Cloud：AI/ML operational excellence](https://docs.cloud.google.com/architecture/framework/perspectives/ai-ml/operational-excellence) 强调代码、数据和模型版本管理、持续监控、灰度发布、告警和回滚。
- [NIST：Generative AI Profile](https://www.nist.gov/publications/artificial-intelligence-risk-management-framework-generative-artificial-intelligence) 提供覆盖 AI 全生命周期的 Govern、Map、Measure、Manage 风险管理框架。

## 4. JobRAG 生命周期

### 阶段 0：业务目标与输出契约

**目标：** 在写代码前确定系统回答什么问题，以及什么样的结果算合格。

**需要确定：**

- 目标职位类别；
- 地点、远程、实习/全职和经验级别；
- 数据时间范围；
- 相关岗位的判定方式；
- Role Analysis 和 Job Detail 的路由规则；
- 技能、职责和要求的输出格式；
- 无相关证据时的拒答规则。

**验收结果：** 一份可以用于编写测试问题的业务契约，而不是泛泛的“让系统回答岗位问题”。

### 阶段 1：岗位数据与知识库生命周期

**目标：** 让岗位数据可追踪、可更新、可去重、可重新索引。

每条岗位记录至少保留：

- `job_id`；
- 来源平台和原始 URL；
- 职位、公司、地点和工作类型；
- 发布时间和抓取时间；
- 原始描述和规范化描述；
- 内容哈希；
- 当前有效状态；
- 数据集版本和索引版本。

**必须支持：**

- 增量抓取；
- 新岗位写入；
- 描述变化检测；
- 重复岗位合并；
- 过期岗位标记；
- 变更后的增量分块和 Embedding；
- 索引版本切换与回滚。

**当前生命周期策略：**

- 以岗位 `date_posted` 为主要时间依据，超过 60 天的岗位标记为失效；缺少发布时间时使用 `last_seen_at`；
- 失效岗位默认不参与检索、统计和问答，原始岗位与历史快照继续保留用于审计；
- 失效岗位的 chunk 和 Embedding 从当前检索索引中移除；
- 新增或内容变化的岗位只重建自身 chunk 和 Embedding，不触碰未变化岗位的向量；
- 每次服务启动和抓取入库后自动执行生命周期检查，也可通过维护接口手动执行。

**数据质量检查：**

- 描述是否为空或过短；
- URL 是否有效；
- 是否有重复岗位；
- 发布时间是否异常；
- 公司和职位字段是否缺失；
- 岗位是否已经过期。

**结构化 Chunk 规则：**

- 优先识别并保留职位概述、职责、任职要求、加分项、技能、经验、教育、项目/研究和工作安排等章节；
- 过滤公司背景、福利、薪资、申请流程和法律声明等低相关内容；
- 章节内优先按段落或列表项成块，只有超长文本才按长度切分并保留少量重叠；
- 每个 chunk 保留 `job_id`、职位、公司、地点、职位类型、章节、顺序和内容哈希；
- 没有明确章节的岗位使用未结构化文本回退策略，不能因章节识别失败而直接丢弃岗位。

### 阶段 2：面向目标职位的岗位级检索

**目标：** 先找到相关岗位，再在这些岗位中分析要求。

检索流程分为两层：

1. 使用关键词、BGE 向量、混合检索和元数据过滤，生成约 30～50 个内部候选岗位；
2. 对候选岗位按 `job_id` 聚合和排序，直接取其中 8～12 个最相关岗位作为分析样本与引用来源。

岗位级排序使用混合检索相关性（80%）和有效章节覆盖度（20%）。标题与概念命中已经包含在 BM25/BGE 候选检索中，不在最终排序中重复加权；用户未指定 PhD 时，对 PhD 专属岗位施加小幅约束惩罚。同一公司同一职位的 PhD/年份重发变体只保留一个，避免近重复岗位占满分析样本。

重要约束：

- 候选集以 `job_id` 为单位，而不是以 chunk 数量为单位；
- 同一岗位的多个 chunk 不能制造虚假的高频率；
- 技能频率按“最相关岗位中出现该技能的岗位数量”统计；
- 最相关岗位同时用于分析、上下文恢复和引用，不再单独建立另一套证据岗位集合；
- 全知识库统计只能作为明确请求的辅助分析，不应是默认问答路径。

**示例：**

如果最相关的 10 个 AI Agent 实习岗位中，Python 出现在 8 个岗位，RAG 出现在 6 个岗位，Kubernetes 出现在 2 个岗位，则输出应明确说明统计分母为这 10 个岗位，而不是按 chunk 次数或整个知识库统计。

**验收结果：** 能返回去重后的相关岗位集合、岗位级技能统计和每个结论对应的证据。

### 阶段 3：基于证据的问答

回答生成必须使用结构化证据，而不是把所有文本直接拼接给 LLM。

推荐回答结构：

1. 分析范围与样本数量；
2. 核心技能和硬性要求；
3. 常见但非必需的技能；
4. 加分项；
5. 职责和技术栈归纳；
6. 具体岗位证据和来源链接；
7. 结论限制与不确定性。

生成约束：

- 只允许基于检索到的岗位证据作出事实性陈述；
- 不能把模型常识伪装成岗位数据结论；
- 每个频率或比较结论都必须能回溯到岗位集合；
- 没有足够证据时，应降低结论强度或拒答；
- 薪资等数值比较必须检查检索岗位中的金额证据；没有金额，或比较样本披露不完整时，直接说明证据不足，不调用模型补充推测；
- 岗位描述应被视为不完全可信的外部文本，不能覆盖系统级指令。

### 阶段 4：离线评估与质量门禁

评估分为三层。

#### 检索层

- Job-level Recall@K；
- NDCG；
- 相关岗位覆盖率；
- 去重后有效岗位数量；
- 元数据过滤准确性。

#### 分析层

- 技能是否按岗位去重；
- 技能频率是否正确；
- 是否混入不相关岗位；
- 是否保留时间和来源信息。

#### 回答层

- Groundedness：回答是否有证据支持；
- Relevance：是否回答了用户问题；
- Completeness：是否覆盖关键要求；
- Citation Coverage：重要结论是否有引用；
- Refusal Quality：证据不足时是否正确拒答。

评估数据集应版本化，至少包含典型问题、筛选条件、相关岗位标注和预期输出要点。大规模测试可以使用自动评估或 LLM Judge，但应保留一小组人工校准样本，避免完全依赖模型评判。

人工标注未覆盖所有新增岗位时，未知岗位不得自动视为无关。检索质量同时使用 Recall@8 和基于已知正相关等级的 condensed NDCG@8；参数只在 development 集选择，发布门禁只读取独立 test 集结果。后续人工标注界面必须区分“未判断”和“明确无关”。

每次修改 Embedding、chunk、检索权重、Prompt 或 LLM 后，应运行回归评估，并记录配置和结果。

### 阶段 5：运行维护、成本和可观测性

系统运行后需要记录：

- 查询和检索延迟；
- LLM 调用次数和 Token 数；
- DeepSeek 成本；
- 缓存命中率；
- 无结果和拒答比例；
- 检索分数和候选岗位数量；
- 引用覆盖情况；
- Embedding 和 LLM 失败率；
- 岗位数据新鲜度。

维护机制包括：

- 定时抓取和增量索引；
- 按语料版本、模型版本和 Prompt 版本管理缓存；
- 向量不可用时回退到 BM25；
- LLM 超时、限流和失败重试；
- 新模型或 Prompt 的对比测试；
- 索引、Prompt 和模型版本回滚；
- 数据漂移和质量下降告警。

对于当前个人项目规模，不需要立即引入 Kubernetes、分布式向量数据库或复杂的多租户权限系统。SQLite FTS、BGE-M3、本地缓存和 DeepSeek API 足以支撑原型和求职展示，但接口和数据结构应为未来扩展保留版本字段。

### 阶段 6：安全、合规与数据治理

需要遵守数据来源平台的使用条款、访问限制和适用的隐私要求。系统还应：

- 将 API Key 放在环境变量中；
- 对日志中的个人信息进行脱敏；
- 保留岗位来源和抓取时间；
- 限制不必要的原始数据暴露；
- 将检索文本视为外部不可信输入；
- 多用户部署时增加身份认证、权限过滤和数据隔离。

## 5. 当前实现与目标的差距

### 已实现并可用于个人上线

- JobSpy 岗位采集；
- 岗位持久化和描述补全；
- 语义分块；
- 本地 BGE-M3 Embedding；
- SQLite FTS/BM25 与向量混合检索；
- DeepSeek 证据型问答；
- 引用和拒答路径；
- 版本化缓存；
- 岗位生命周期管理（60 天过期、重新出现时恢复）；
- 岗位级检索、去重、排序与目标岗位技能分析；
- 引用校验、证据回退和可配置拒答；
- 检索/回答/索引质量评估与质量门禁页面；
- 运行监控、延迟统计、缓存命中、Token 和匿名请求追踪。
- 每日 09:00（新加坡时间）增量抓取；默认每来源最多 10 条、回看 72 小时，失败来源最多重试一次；每次最多本地 Embedding 100 个片段。
- Embedding 失败按片段持久记录，自动重试最多 3 次；成功后清除失败状态，连续失败的片段从自动队列暂停，提供手动重试入口。状态区报告失败数量、停止自动重试数和最早待处理时长；待处理超过 100 个且最早片段超过 24 小时、最早待处理超过 72 小时，或存在失败片段时显示告警。

### 生产化阶段仍需补齐

1. 让自动抓取脱离本地 Web 服务进程运行，支持机器休眠/服务关闭后的补跑，并增加失败任务告警；
2. 增加数据库备份、恢复和数据迁移流程；
3. 增加 API 认证、权限控制和公开部署的 HTTPS；
4. 完善 Groundedness、Completeness 和拒答回归评估；
5. 增加索引、Prompt、模型和配置的正式回滚机制；
6. 根据使用量再考虑 Docker、PostgreSQL/pgvector、多用户隔离等扩展。

## 6. 推荐的后续开发顺序

后续真实业务开发按以下顺序推进：

1. 确定阶段 0 的业务目标和输出契约；
2. 实现目标职位条件下的 job-level 候选集；
3. 实现候选岗位内的技能和要求分析；
4. 完善带证据和引用的问答输出；
5. 建立端到端评估和回归门禁；
6. 建立数据更新、缓存、监控和回滚；
7. 最后根据实际使用量增加安全、权限和扩展性能力。

## 7. 设计决策记录

- **主要用户目标：** 求职者针对具体职位类别研究招聘市场要求。
- **默认统计范围：** 与用户问题和过滤条件相关的岗位候选集。
- **全库统计定位：** 仅在用户明确询问知识库整体分布时使用。
- **默认检索策略：** 元数据过滤 + BM25 + 本地 BGE 混合检索，再进行岗位级去重和分析。
- **默认 LLM：** DeepSeek 用于有证据的回答生成，不负责替代检索事实。
- **质量原则：** 可追溯、可评估、可更新、可拒答、可回滚。
- **开发协作原则：** 每完成一个阶段先报告结果，并经用户确认后开始下一阶段。

## 8. 运行维护与可观测性（已实现）

- 每次正式问答记录匿名追踪号、请求状态、检索/LLM/总耗时、缓存命中、候选岗位数、证据数与 Token 用量。
- 日志只保存问题 SHA-256 和字符数，不保存原始问题、系统 Prompt、岗位上下文或密钥；默认保留 30 天。
- 管理页展示近 7 天 P50/P95 延迟、缓存命中率、错误/无结果、Token/可选成本、数据新鲜度与索引覆盖。
- 记录 Embedding、LLM、问答流水线和语料版本，为问题定位与后续回滚提供依据。
- 成本单价不硬编码；通过环境变量维护当前供应商价格，避免过期价格造成错误估算。

## 9. 当前上线状态与面试表达

### 当前上线结论

系统已适合个人使用和小范围内测：核心采集、索引、检索、问答、评估和维护链路已经贯通。本阶段的“上线”指本地或受控环境上线，不等同于面向公众的高并发生产发布。自动抓取、备份恢复、认证权限和 HTTPS 暂列为生产化工作，不阻塞当前使用。

### 面试介绍时可展开的主线

1. **数据链路：** JobSpy 采集岗位，进行去重、结构化分块、Embedding 和增量索引。
2. **检索链路：** 元数据过滤结合 BM25 与 BGE-M3 向量检索，在岗位级合并、去重和排序。
3. **回答链路：** 只把最相关岗位作为证据交给 DeepSeek，输出岗位级分析、引用和证据不足说明。
4. **质量链路：** 使用检索指标、引用校验、拒答检查和索引覆盖率进行回归评估。
5. **工程链路：** 通过缓存、生命周期管理、运行指标、Token 统计和版本记录控制成本并支持排障。
6. **后续演进：** 从个人可用版本扩展到自动更新、备份、安全和可回滚的生产版本。
